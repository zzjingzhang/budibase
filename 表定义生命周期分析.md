### 1.2 schema 权限回退的实现

schema 权限回退机制实现在 [authorized.ts](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/middleware/authorized.ts#L84-L178) 中。

#### 核心逻辑

当 `opts.schema = true` 时，权限检查会进行"回退"尝试：

1. **首次权限检查**：使用请求的权限级别（如 `PermissionLevel.READ`）检查资源权限
2. **权限回退**：如果首次检查失败，且 `opts.schema = true`，则使用另一个权限级别（如 `PermissionLevel.WRITE`）再次检查

关键代码片段（[authorized.ts#L164-L174](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/middleware/authorized.ts#L164-L174)）：

```typescript
try {
  // check authorized
  await checkAuthorized(ctx, resourceRoles, permType, permLevel!)
} catch (err) {
  // this is a schema, check if
  if (opts && opts.schema && permLevel) {
    await checkAuthorized(ctx, otherLevelRoles, permType, otherLevel)
  } else {
    throw err
  }
}
```

#### 另一个权限级别的计算

`otherLevel` 的计算方式（[authorized.ts#L105-L108](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/middleware/authorized.ts#L105-L108)）：

```typescript
const otherLevel =
  permLevel === PermissionLevel.READ
    ? PermissionLevel.WRITE
    : PermissionLevel.READ
```

这意味着：
- 如果请求的是 **READ** 权限，回退检查 **WRITE** 权限
- 如果请求的是 **WRITE** 权限，回退检查 **READ** 权限

#### 为什么需要 schema 权限回退

schema 权限回退是为了处理表结构（schema）的特殊权限场景。表作为一种资源，其结构定义（schema）的访问权限可能与数据访问权限不同。通过 schema 回退机制：

- 用户即使没有表的 READ 权限，但如果有 WRITE 权限，仍然可以读取表的结构定义
- 反之亦然，确保对表结构的访问能够通过任一方向的权限检查

这种设计允许更灵活的权限控制，特别是在构建器场景中，用户可能需要查看表结构来进行配置，但不一定需要读取表中的数据。

## 2. save 中 guardTable 对 default 和 primaryDisplay 的限制

### 2.1 guardTable 函数

`guardTable` 函数定义在 [table/index.ts](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/api/controllers/table/index.ts#L109-L128)，在保存表之前进行验证：

```typescript
async function guardTable(table: Table, isCreate: boolean) {
  checkDefaultFields(table)

  if (
    table.primaryDisplay &&
    !canBeDisplayColumn(table.schema[table.primaryDisplay]?.type)
  ) {
    // Prevent throwing errors from existing badly configured tables. Only throw for new tables or if this setting is being updated
    if (
      isCreate ||
      (await sdk.tables.getTable(table._id!)).primaryDisplay !==
        table.primaryDisplay
    ) {
      throw new HTTPError(
        `Column "${table.primaryDisplay}" cannot be used as a display type.`,
        400
      )
    }
  }
}
```

### 2.2 default 字段限制

`checkDefaultFields` 函数（[table/index.ts#L71-L83](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/api/controllers/table/index.ts#L71-L83)）：

```typescript
function checkDefaultFields(table: Table) {
  for (const [key, field] of Object.entries(table.schema)) {
    if (!("default" in field) || field.default == null) {
      continue
    }
    if (helpers.schema.isRequired(field.constraints)) {
      throw new HTTPError(
        `Cannot make field "${key}" required, it has a default value.`,
        400
      )
    }
  }
}
```

#### 限制规则

- **不能同时设置 default 值和 required 约束**
- 如果字段有默认值（`default != null`），则不能将该字段设为必填（required）
- 这是为了避免逻辑冲突：既然有默认值，就不应该要求用户必须提供值

```typescript
export async function create(
  table: WithoutDocMetadata<Table>,
  rows?: Row[],
  userId?: string
): Promise<Table> {
  let createdTable: Table
  if (isExternal({ table })) {
    createdTable = await external.create(table)

    createdTable = await internal.create(table, rows, userId)

  await setPermissions(createdTable._id!, {
    writeRole: roles.BUILTIN_ROLE_IDS.ADMIN,
    readRole: roles.BUILTIN_ROLE_IDS.ADMIN,

  return createdTable
```

## 4. publish(tableId) 的完整流程

`publish` 控制器定义在 [table/index.ts#L323-L469](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/server/src/api/controllers/table/index.ts#L323-L469)。

### 4.1 流程总览

```
开始
  ↓
检查表是否存在
  ↓
检查是否为外部表（外部表不支持发布）
```

### 4.4 seedProductionTables = true 时复制 dev 行到 prod

```typescript
if (seedProductionTables) {
  try {
    const devDb = context.getWorkspaceDB()
    const devRows = await devDb.allDocs(
      getRowParams(tableId, null, {
        include_docs: true,
      })
    )
    const importRows = devRows.rows
      .map(({ doc }: any) => doc)
      .filter(doc => doc && !doc._deleted)
      .map(doc => {
        const { _rev, _attachments, ...rest } = doc
        return rest
      })

    if (importRows.length) {
      await context.doInWorkspaceContext(prodWorkspaceId, async () => {
        const prodDb = context.getWorkspaceDB()
        const existingProdRows = await prodDb.allDocs(
          getRowParams(tableId, null, {
            include_docs: true,
            limit: 1,
          })
        )
        const hasProdRows = existingProdRows.rows.some(
          (row: any) => row.doc && !row.doc._deleted
        )
        if (hasProdRows) {
          return
        }

        const prodTable = await sdk.tables.getTable(tableId)
        const sanitizedRows = stripIgnoreTimezoneSuffix(importRows, prodTable)
        await handleDataImport(prodTable, {
          importRows: sanitizedRows,
          userId: ctx.user._id,
          identifierFields: ["_id"],
        })
      })
    }
  } catch (error) {
    console.warn(
      `Failed to copy dev rows to prod for table ${tableId}`,
      error
    )
  }
}
```

#### 复制逻辑

1. 从开发环境数据库获取该表的所有行
2. 过滤掉已删除的文档
3. 移除 `_rev` 和 `_attachments` 字段
4. 切换到生产环境上下文
5. **检查生产环境是否已有数据**：如果已有数据则跳过（避免覆盖）
6. 处理时区忽略的列（`stripIgnoreTimezoneSuffix`）
7. 使用 `handleDataImport` 导入数据，以 `_id` 作为标识字段

#### 注意事项

- 复制操作在 try/catch 中，失败不会阻止发布流程
- 只有生产环境没有数据时才会复制（保护生产数据）
- 处理时区问题：如果列设置了 `ignoreTimezones`，移除 `Z` 后缀

### 4.5 Replication.filter 过滤同步

```typescript
const tableSegment = `${SEPARATOR}${tableId}${SEPARATOR}`
const matchesTable = (_id: string) =>
  _id === tableId ||
  _id.endsWith(`${SEPARATOR}${tableId}`) ||
  _id.includes(tableSegment)
const isDataDoc = (_id: string) =>
  _id.startsWith(`${DocumentType.ROW}${SEPARATOR}`) ||
  _id.startsWith(`${DocumentType.LINK}${SEPARATOR}`)

const replication = new dbCore.Replication({
  source: dbCore.getDevWorkspaceID(appId),
  target: prodWorkspaceId,
})

await replication.resolveInconsistencies([tableId])

await replication.replicate(
  replication.appReplicateOpts({
    tablesToSync: undefined,
    checkpoint: false,
    filter: (doc: any) => {
      const _id = doc?._id as string
      if (!_id || _id.startsWith("_design")) {
        return false
      }
      if (_id.startsWith(DocumentType.AUTOMATION_LOG)) {
        return false
      }
      if (_id.startsWith(DocumentType.WORKSPACE_METADATA)) {
        return false
      }
      if (!matchesTable(_id)) {
        return false
      }
      if (!seedProductionTables && isDataDoc(_id)) {
        return false
      }
      return true
    },
  })
)
```

#### 过滤规则

1. **排除设计文档**（`_design` 开头）
2. **排除自动化日志**（`DocumentType.AUTOMATION_LOG` 开头）
3. **排除 workspace metadata**（`DocumentType.WORKSPACE_METADATA`）
4. **只保留与目标表相关的文档**（`matchesTable`）
   - 表文档本身（`_id === tableId`）
   - 以 `:tableId` 结尾的文档
   - 包含 `:tableId:` 片段的文档（如行文档 `ro_xxx:ta_tableId:...`）
5. **数据文档的条件同步**：
   - `seedProductionTables = true`：同步数据文档（行和链接）
   - `seedProductionTables = false`：不同步数据文档，只同步表结构

#### matchesTable 的匹配逻辑

`tableSegment` 为 `:tableId:`，用于匹配包含该表 ID 的文档 ID：

- **表文档**：`ta_table123` → `_id === tableId`
- **行文档**：`ro_xxx:ta_table123:rowid` → 包含 `:ta_table123:`
- **链接文档**：`link_xxx:ta_table123:...` → 包含 `:ta_table123:`

#### Replication.appReplicateOpts 的基础过滤

除了自定义 filter，`appReplicateOpts` 还会添加一些基础过滤逻辑（[Replication.ts#L115-L193](file:///Users/zhangjing/Desktop/so-coders/0604-under/budibase/packages/backend-core/src/db/Replication.ts#L115-L193)）：

- 非创建模式下排除迁移设计文档
- 同步到 dev 时排除设计文档
- 始终同步已删除的文档（tombstone）
- 始终同步用户元数据
- 同步到生产且非创建时排除自动列状态
- 数据文档根据 `tablesToSync` 或 `syncAllTables` 判断

- 两者都设置为当前时间（ISO 格式）

#### 注意事项

- 如果生产环境 metadata 不存在，抛出错误（要求先发布 workspace）
- 更新后使缓存失效（`invalidateWorkspaceMetadata`）
- 返回 `tableId` 和 `publishedAt` 给客户端

---

## 总结

表定义生命周期涉及多个关键环节：

1. **读取阶段**：通过 schema 权限回退机制，确保用户可以通过任一权限级别（READ/WRITE）访问表结构
2. **保存阶段**：通过 `guardTable` 验证 default 字段不能与 required 同时存在，以及 primaryDisplay 列类型的合法性
3. **创建 vs 更新分派**：创建操作统一走 `sdk.tables.create`，更新操作通过 `pickApi` 分派到内部表或外部表的更新逻辑
4. **发布阶段**：
   - 未发布 workspace 时先完整发布 workspace
   - `seedProductionTables=true` 时将开发环境数据复制到生产（仅当生产无数据时）
   - 使用 `Replication.filter` 精确控制只同步目标表相关的文档（表定义、链接文档、可选的数据行）
   - 更新 metadata 中的发布和部署时间戳
